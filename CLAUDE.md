# OW Slido — project notes for agents

- Product spec: `tasks/prd-slido-clone.md` (MVP). Stories live in `scripts/ralph/prd.json`; progress log is `scripts/ralph/progress.txt`.
- Stack: Next.js (App Router) + TypeScript, PostgreSQL, Socket.IO via a custom server. Node 22.
- Environment: Postgres 16 on localhost. Dev DB `ow_slido`, test DB `ow_slido_test`, credentials in `.env.local` (gitignored, never commit or print it). Do not touch other databases on this Postgres server.
- Redis and Docker are NOT installed. Use in-memory adapters behind interfaces (rate limiter, pub/sub); do not try to install system packages.
- Use only the npm registry for dependencies; no global installs.
- Run `npm run lint`, `typecheck`, `test` before every commit.

## Database commands
- Drizzle ORM + `pg`. Schema in `db/schema.ts`, generated SQL in `db/migrations/`, client factory in `db/client.ts` (`createDb(url)`).
- `npm run db:generate` — generate a migration after editing the schema (commit the output).
- `npm run db:migrate` — apply migrations to `DATABASE_URL`; `npm run db:migrate:test` — to `TEST_DATABASE_URL`.
- `npm run db:reset:test` — drop and recreate the test DB's schemas, then migrate (refuses to run on the dev DB).
- Tests that hit the DB: start the file with `// @vitest-environment node`, use `createTestDb()` and `truncateAll(db)` in `beforeEach` from `tests/helpers/db.ts`. Run `db:migrate:test` first after adding migrations.

## Workspaces
- Events belong to a workspace (`events.workspace_id`, NOT NULL, cascade); `events.owner_id` is only the creator. Users reach workspaces through `memberships`.
- Every data table must reach a workspace through `events` (or `interactions`, which reach `events`), so deleting a workspace removes everything. A table that holds workspace-level data (not event data) references `workspaces` directly with `onDelete: "cascade"`.
- Access: `requireMember(request)` (`lib/auth/require-admin.ts`) resolves the active workspace (cookie `workspace`, else first active membership) and returns `{user, workspaceId, role}`; use `getSessionMember` where anonymous callers are also allowed. Find events with `findOwnedEvent(id, auth.workspaceId)`; pages and the socket server use `resolveActiveMembership` from `lib/auth/workspace.ts`. Test users who act as hosts or strangers need a workspace (`workspaceFor`), else they get 403.
- Tests that insert events directly need `workspaceId: await workspaceFor(db, user.id)` from `tests/helpers/db.ts`. In routes, `lib/workspaces.ts` has `createPersonalWorkspace` and `firstWorkspaceId`.

- Members: `lib/members.ts` holds the rules (admins cannot touch owners or grant owner, last active owner is protected under a row lock, no self-suspend) behind `/api/members` routes. Changing a role, suspending or removing a member also calls `revokeMemberSockets` (lib/realtime/publisher.ts) so their live host sockets drop; HTTP access ends on the next request because memberships are read per request.

## Interactions
- Types: `poll`, `wordcloud`, `sharedNotes`, `openText`, `rating`. Config for the last three is validated in `lib/interaction-config.ts` (hand-written parsers; no zod). Adding a type means updating the `db/schema.ts` enum and check, the create/PATCH/duplicate routes and a migration.
- Every table that holds event data (responses, notes, analyses...) must reference `interactions` or `events` with `onDelete: "cascade"`, so deleting an event removes it. Add a cascade test for each new table.
- `qa` is an interaction type (config `prompt`, `moderation`; title defaults to "Q&A"). `questions.interaction_id` is NOT NULL, so anything that inserts a question needs an interaction: routes use `ensureQaInteraction(db, eventId)` (lib/questions.ts; first Q&A of the event, created if none: live when nothing else is live, else paused) and tests use `qaFor(db, eventId)` from `tests/helpers/db.ts`. Migration 0031 has a hand-written reverse in `db/migrations-down/` (Drizzle never runs it); tests/qa-interaction.test.ts rehearses both in a scratch schema.
- Q&A routes: `lib/question-routes.ts` holds the handlers once. `/api/interactions/[id]/questions` (POST ask, GET approved), `/queue` (host: pending + approved), `/[questionId]` (PATCH moderate, DELETE) and `/[questionId]/upvote` take the Q&A id; the old `/api/events/[id]/questions…`, `/moderation`, `/present/questions` and `/api/questions/[id]/upvote` resolve to the event's live Q&A, else its first (`resolveEventQa`), and moderate a question in whichever Q&A it sits. Moderation and `profanityFilter` (default on) come from the Q&A's `config`; the event-level `moderationMode` PATCH copies the mode onto the event's Q&As. Every `question:*` socket message carries `interactionId`; clients must filter on it once an event shows more than one Q&A.
- Host Q&A as content: every new event gets one draft Q&A (`POST /api/events`, position 0, moderation from the event's `moderationMode`, which is only that default and never read for live behavior; the event PATCH no longer touches Q&As). `PollManager` builds Q&As like other types (name = title, prompt, moderation, profanity filter). A started Q&A can still switch `moderation`/`profanityFilter` through the interaction PATCH (title/prompt answer 409); other types stay draft-only. `resolveEventQa` puts drafts last. While every Q&A of an event is a draft, participants get `notOpen: true` in `getParticipantQa` and the event-level submit answers 409 `api.qaNotOpen`, so tests that ask a question on an event made through `POST /api/events` must first set its Q&A `live`. The moderation panel and `GET /api/events/[id]/moderation?interaction=` work on one Q&A at a time; the presenter follows the live (else first) Q&A, drops `question:*` messages for other `interactionId`s and shows a live Q&A by itself when nothing else is live.
- Participant Q&A tab: `getParticipantQa(eventId, participantId)` (lib/questions.ts, also `GET /api/events/[id]/qa`) returns `{current, earlier}`: the live Q&A, else the latest paused/closed one (read-only), plus the other closed ones; drafts never show. `QaTab` posts and upvotes through the `/api/interactions/[id]/...` paths, filters socket messages on `interactionId` and refetches on `state-changed`. A closed Q&A refuses questions (409 `api.qaClosed`); paused is read-only in the UI only. `ensureQaInteraction` creates the Q&A `live` when nothing else is live, else `paused` (same rule as migration 0031).

- Module registry (`lib/interaction-modules.ts`): one `InteractionModule` per type (`validateConfig`, `results`, `csv`, `responseCount`, plus `presenter(row)` and `live(row, participantId)` for the two screens). `lib/export.ts`, `lib/presenter.ts`, `lib/live-view.ts` and `responseCounts` only dispatch through `interactionModule(row.type)`; never switch on the type there. A new type is added to the enum/check, `INTERACTION_MODULES` (its order is the table order of the event CSV) and nothing else in those files; tests/interaction-modules.test.ts fails when a stored type has no module. `csv` returns tables (`header`, `rows`, optional `trailing`); same-header tables of one event are merged into one file, and `tablesToCsv` joins tables with a blank line.

- Ranking (`ranking`, a `NEW_INTERACTION_TYPES` member): config `prompt` + `options: [{id, text}]` (2-10, text ≤ 80; limits in `lib/ranking-limits.ts`, client-safe). `lib/ranking.ts` holds `scoreRanking` (1st = N points … last = 1, ties share a rank), `submitRanking` and `isPermutation`; `POST /api/interactions/[id]/ranking {order}` is one submission per participant (unique constraint, 409 `api.alreadyRanked`), live only, and publishes host-only `ranking:results`. Results carry `positions` (per-position counts); the CSV has fixed `position_1`..`position_10` columns (empty past the option count) so ranking tables of different sizes still merge into one file. Ranking is not on Free, so tests that create one need `setPlan(db, workspaceId, "pro")`. `copyConfig` gives copied options new ids.
- Ranking participant screen (`components/ranking-form.tsx`): the module's `live` returns `LiveRanking` with `mine` (the participant's submitted order, so a reload shows "Answer sent"). Drag uses window-level pointer listeners while dragging, never pointer capture: React moves the dragged row in the DOM and Chrome then drops the capture. Up/down buttons use `aria-disabled` at the ends (not `disabled`) and focus goes back to the used button after the reorder.
- Ranking host side: `PollManager` builds a ranking from the poll option fields (draft option `label` is sent as `text`; config reads back `text`). The module's `presenter` returns `PresenterRanking` for live/closed (`presentWhenClosed`), `PresenterView` follows host-only `ranking:results`; `PresenterRanking` prints `#rank` and points, the bar only repeats them.

- Event ZIP (`GET /api/events/[id]/export.zip`, `buildEventZip` in lib/export.ts): one CSV per interaction named `NN-Title.csv` (list order, not the stored `position` value), each from `buildInteractionCsv`; the archive is written by `createZip` (lib/zip.ts, store-only, no dependency). It needs `export` and the `csv` report format, so Free can use it. A new type's files appear without changes here.

- Content library (event page, `PollManager`): one list of every type with icon + type name, state and response count (`responseCounts` in lib/content-library.ts, returned by `GET /api/events/[id]/interactions` as `counts`). Reorder is drag plus ↑/↓ buttons on every row; rename and delete are draft-only (409 otherwise), duplicate works in any state. "Add content" is a menu (`AddContentMenu`) that keeps plan-locked types as `PlanHint` links. Create, PATCH, duplicate, reorder and delete publish host-only `content:changed`; `PollManager liveUpdates` refetches on it and on state/response messages (coalesced). A test that records every published message must clear it after creating its interaction through the route.

- Templates (`templates` + `template_items`, cascade from `workspaces`; `lib/templates.ts`): content only (type, title, config; no state, responses, participants, questions or notes). Config always goes through `copyConfig` (lib/interaction-copy.ts, shared with the duplicate route), which gives poll options new ids. Routes: `/api/templates` (GET for every member, POST save `{eventId, interactionId?, name?}` needs `templates.manage`), `/api/templates/[id]` (PATCH rename, DELETE; `templates.manage`), `POST /api/events/[id]/interactions/from-template` (`event.edit`; 402 for a type the plan lacks, nothing added) and `POST /api/events/from-template` (`event.create`; types the plan lacks are left out and counted in `skipped`). The count limit is `assertTemplateSlot` (lib/limits.ts, 402 `template_limit`), taken under a lock on the workspace row. A new image-bearing config must be copied by `copyConfig`.
- Templates UI: `/dashboard/templates` (`TemplatesManager`; everyone reads, `templates.manage` renames/deletes), nav link for every member. On the event page `PollManager` takes `canManageTemplates` and `eventName`: per-row and whole-event "Save as template" (`SaveTemplateDialog`) and "Add from template" (`TemplatePicker`, loads `GET /api/templates` each time it opens). The dashboard form's Template select posts to `/api/events/from-template` and reports `skipped`. Failed calls go through `apiError` (lib/api-error.ts: message plus a `Lock` on 402) and `PlanError`, so a plan limit shows the tier link. Buttons inside dialogs that call the API must not be `disabled` while pending (focus would leave the dialog and Escape would stop working); guard in the handler and set `aria-busy`.

- Quiz (`quiz`, a `NEW_INTERACTION_TYPES` member): config `prompt`, `options: [{id, text}]` (2-6, text ≤ 80), `correctOptionIds` (≥ 1, each an option id), `timeLimitSeconds` 5-120 (default 20), `points` (default 1000); limits in `lib/quiz-limits.ts`. Options need their ids in the body, since `correctOptionIds` refers to them; a PATCH that changes `options` must restate `correctOptionIds` (the route re-checks the merged config with `quizConfigError`). `startInteraction` writes `interactions.started_at`/`deadline_at` from the database clock (`now()` + time limit) every time a quiz question starts or resumes, so a resume opens a fresh window; other types leave them null. `quiz_answers` holds one row per participant per question (`option_ids`, `elapsed_ms`, `correct`, `points`). Quiz is not on Free. `copyConfig` gives copied options new ids and remaps `correctOptionIds`.
- Quiz answers: `POST /api/interactions/[id]/quiz-answer {optionIds}` (`submitQuizAnswer`, lib/quiz.ts): live only, one per participant (409 `api.alreadyAnswered`), 409 `api.quizTimeUp` after `deadline_at` plus `QUIZ_GRACE_MS` (default 300). Elapsed time and the deadline check use the database `clock_timestamp()`, never the client's. `scoreQuizAnswer` scales points linearly from 100% to 50% at the deadline; correct means the selected set equals `correctOptionIds`. Publishes host-only `quiz:results` (`QuizResults`: per-option counts with `correct` flags, `correctPercent`); the CSV has `option,correct,count,answers,correct_percent` and no participants.

- Quiz participant screen (`components/quiz-form.tsx`): the module's `live` returns `LiveQuiz` (options without the correct ones, `multiple`, `deadlineAt` and `serverNow` both from the database clock, `mine`). The countdown is `deadlineAt` minus (server time on arrival + elapsed client time), so a wrong device clock does not matter; seconds are announced only at 10 and 5 (derived text, no effect), the ticking number is `aria-hidden`. One correct option: a tap locks and sends; several: toggle, then "Send answer". After close the client fetches `GET /api/interactions/[id]/quiz-result` (the participant's own outcome plus `correctOptionIds`; 409 until closed, so the answer is never sent while live). `LiveView` keys the form on `id:deadlineAt` so a resumed question restarts its countdown. Answer colours are `--quiz-1..6` and `--quiz-ink` tokens (checked at 4.5:1 in light and dark); each option also has its own shape.

- Quiz host side: the builder in `PollManager` ("New quiz question"): prompt, 2-6 option rows each with a "Correct" checkbox, time limit, points. Option ids are made on the client (`newQuizOption`) because `correctOptionIds` in the same body points at them; an edit restates ids and correct ids. The module's `presenter` returns `PresenterQuiz` for live and closed (`presentWhenClosed`): while live only the answer `total` (from host-only `quiz:results`), no per-option counts and no correct ids; `results` (counts, `correct` flags) only once closed. `PresenterQuiz` is keyed on `id:deadlineAt:state`, so a resume restarts its countdown; "Close and show answer" on the presenter posts the normal `/close`, which is the reveal. A rule like `.present-bar-head span:last-child { white-space: nowrap }` also hits spans nested in the head: override with a more specific selector (see `.present-quiz-text`).

- Quiz leaderboard (`lib/leaderboard/`): `LeaderboardStore` (add, top, rankOf, size, reset, replaceAll) with `MemoryLeaderboardStore`, held on `globalThis` (`getLeaderboardStore`/`setLeaderboardStore`; tests install a fresh one in `beforeEach`). Totals are persisted in `quiz_scores` (event + participant, points, answered_count, total_elapsed_ms) by `closeInteraction` inside its transaction (`persistClosedQuestion`), and added to the store after commit (`applyScoreDeltas`); a quiz question that is only live or paused counts for nothing, and a question closes once. Rank = points, then less total time; equal on both shares a rank; someone who answered nothing is not ranked. `rebuildLeaderboard()` reloads the table at server start (server.ts). `POST /api/events/[id]/leaderboard/reset` (`live.run`) deletes the rows and resets the store. Scores hang off the participant id, so a rejoin with the same token keeps score and nickname.

- Quiz nickname (`lib/nickname.ts`, `PUT /api/events/[id]/nickname {nickname}`, participant token): 1-20 characters (`NICKNAME_MAX` in lib/quiz-limits.ts), whitespace collapsed, no control characters, `isProfane` list; taken names (case-insensitive, per event) answer 409 `api.nicknameTaken`, backed by the unique index `participants_event_nickname_unique` (a race gives the same 409). After the participant's first `quiz_answers` row in the event the name is fixed (409 `api.nicknameLocked`). `LiveQuiz` carries `nickname` and `nicknameLocked`; `QuizForm` (given `eventId`) shows `NicknameForm` instead of the options until a name exists, then "Playing as X" with Change until the first answer. The server does not require a nickname to answer; US-046 must show a fallback for a participant with none. The leaderboard and CSV (US-046) are the only places a nickname may appear in quiz output.

- Quiz standings on screen (`lib/leaderboard/standings.ts`): `topStandings` (store top n + nicknames; `null` nickname shows the "Player" fallback), `ownStanding` (rank, points, players) and `allStandings` (from `quiz_scores`, with `correct_count`, for the CSV). A closed quiz question's `PresenterQuiz.leaderboard` is the top 10 (null while live); `getQuizOutcome` adds `standing` for the participant. `GET /api/events/[id]/leaderboard?limit=` (`live.run`) feeds the podium. "End quiz" is a presenter screen, not stored state: `PresenterScreen` `podium` (`?view=podium`, button "End quiz and show podium", offered once the event has a quiz and none is live) shows the top 3 and the participants keep their last question result. Only the event's first quiz question (position, then creation) carries the `leaderboard` CSV table (`section,rank,nickname,points,correct_answers`), so the event CSV and the ZIP list it once; nicknames appear nowhere else in exports. `quiz_scores.correct_count` is written with the points when a question closes (a host reset clears it with them).

- Quiz results are pushed, not fetched: when a quiz question closes, `closeInteraction` calls `publishQuizOutcomes` (lib/quiz.ts), which sends each participant `quiz:outcome {interactionId, outcome}` (the `QuizOutcome` shape of `GET quiz-result`) to their own room (`publish(..., {participantId})`, `participantRoom` in lib/realtime/publisher.ts; every participant socket joins it). `QuizForm` (given `socket`) waits for it and calls `quiz-result` only after 3 s without a message, or at once with no socket. Reason: 500 phones fetching at the same moment kept the one Node process busy for over a second. `MemoryLeaderboardStore` keeps the sorted ranking per event until the next change. Load test: `scripts/load/quiz.mjs` (needs a production build and a server on the test DB; steps and the latest numbers in `docs/load-test-quiz.md`); rerun it after changing the close path, the leaderboard store or the quiz screens' requests.

- Survey (`survey`, a `NEW_INTERACTION_TYPES` member): the name is `interactions.title` (`title` in the create body, required, like Q&A); config is only `questions` (1-20, limits in `lib/survey-limits.ts`): `{id, kind: choice|rating|openText, text, required}` plus `options: [{id, text}]` (2-10) and `multiple` for choice, `scale` for rating. A PATCH that sends `questions` replaces the whole list; `copyConfig` gives copies new question and option ids. Storage: `survey_submissions` (one per participant) with `survey_answers` (`question_id`, `value` jsonb: option ids array, rating number or text); a blank optional answer stores no row. `POST /api/interactions/[id]/survey {answers: {questionId: value}}` (`submitSurvey`, lib/survey.ts): live only, 400 with `questionId` (and `missing`, every unanswered required id) on a bad or missing answer, 409 `api.alreadySubmitted` on a second try, profanity filter on open text; publishes host-only `survey:results`. The module's `results` (`SurveyResults`: `total`, `completed`, per-question counts/percent, rating average and distribution, latest open-text answers) and `csv` (one row per submission, columns `1. Question text`..., no identifiers) are registered; `presenter` and `live` stay null until the survey screens (US-049..051). Survey is not on Free, so tests need `setPlan(db, workspaceId, "pro")`.
- Survey host builder (`components/survey-builder.tsx`, opened from `PollManager` via "New survey" / Edit on a draft): its own form, not the shared `Draft`. Question and option ids are made on the client and restated on every save (`surveyBody`, `surveyDraftFrom`). Reorder is ↑/↓ buttons with `aria-disabled` at the ends; focus goes back to the pressed button (`focusNext` selector applied in an effect) and a polite status announces the new position. Unsaved changes: `beforeunload` plus a capture-phase document click guard on `a[href]` (client navigation) that uses `window.confirm`, and a discard `Dialog` on Cancel; both only while the draft differs from the snapshot taken on open. `SurveyPreview` is a disabled read-only picture of the participant form (US-050 builds the real one). Renaming a survey in the list sends `{title}`.

- Survey participant link (`/survey/<interactionId>`, `components/survey-form.tsx`, data from `getSurveyPage` in lib/survey-page.ts): works while the survey is `live`, even beside another live interaction, because migration 0039 exempts `survey` from `interactions_one_live_per_event`. So "the live interaction" means a live non-survey everywhere (`getLiveInteraction`, `getPresenterState`, `ensureQaInteraction`, `startInteraction`: starting a survey pauses nothing, starting anything else leaves a live survey alone; the presenter's next/previous skips surveys). - Survey results screen: a survey is never "the live one", so the projector opens it by id: `/present/<eventId>?view=survey&survey=<id>` (`getSurveyPresenter` in lib/presenter.ts, any state but draft; `GET /api/events/[id]/present?survey=<id>` for resync). `PresenterView` keeps it as the `survey` screen next to `qa` and `podium`, follows host-only `survey:results` and refetches on `state-changed`; a bad id falls back to the normal screen. ## Account and workspace deletion
- `events.owner_id` is nullable and `on delete set null` (migration 0045): deleting a user never deletes events; they belong to the workspace. Nothing should assume an owner exists (`createdBy` was already nullable).
- Workspace delete (`DELETE /api/workspaces/active {name}`, permission `workspace.delete`, owner only; `lib/workspace-deletion.ts`): the name must equal the workspace name after trim (400 `name_mismatch`). `cancelWorkspaceSubscription` asks the billing provider first (`cancelSubscription` once, only for a paid, not yet cancelled subscription with provider ids; free workspaces need no billing set up) and any provider failure or a subscription from another provider (502/503) stops everything, so nothing is deleted while a payment could still be taken. Then one transaction inserts the content-free `deleted_workspaces` row (id, deleted_at, plan; no FK, no name, no email, no audit entry on purpose) and deletes the workspace; the cascade removes the rest. A former member left with no active workspace gets a personal one (`removeWorkspaceRows`). `tests/workspace-deletion.test.ts` walks the FK graph from `workspaces` and fails when a table below it does not cascade or is not seeded; a new workspace-level table needs a row there (ai_calls is the one exception).
- Account delete (`DELETE /api/auth/account {password}`, `lib/account-deletion.ts`, page `/account/delete` linked from the security page): `accountDeletionOutcome` decides per workspace: only member -> workspace deleted with the account (subscription cancelled first), last active owner of a workspace with other members -> 409 `sole_owner` with `workspaces: [{id, name}]` and nothing changes, otherwise only the membership ends. The rule is checked before and again inside the transaction with the membership rows locked. Ownership is transferred with the existing role change on the members page. Audited as `auth.account_deleted` in each workspace the person left (email only in the actor label, like other entries).

## Deleting data
- Event delete (`DELETE /api/events/[id]`, `event.delete`, audited `event.deleted`) relies on cascades only; `tests/participant-data.test.ts` walks the foreign-key graph from `events` and fails when a table below it does not cascade (`ai_calls` is the one exception: it keeps its row with a null event so the daily AI cap cannot be reset). `seedFullEvent` (tests/helpers/seed-event.ts) must get a row in every new data table. The UI asks for the event name through `TypedConfirmDialog` (components/typed-confirm-dialog.tsx: exact match after trim, the button uses `aria-disabled`, the caller returns an error string or null); reuse it for other irreversible actions.
- Participant erasure (`DELETE /api/events/[id]/participants/[participantId]/data`, `event.edit`, `lib/participant-data.ts`): deletes the `participants` row and lets the cascade clear every table with a `participant_id` column, including votes on their question/note and `quiz_scores`; nothing is anonymised and kept. `CONTRIBUTIONS` in that file lists the contribution tables (count shown to the host, interactions to refresh); a test compares it with `information_schema`, so a new table with `participant_id` must be added there. After commit it calls `LeaderboardStore.remove`, publishes `state-changed` for touched interactions and `content:changed`. Audited `participant.data_deleted` (ids and count only). The host UI is `ParticipantData` on the event page (`GET /api/events/[id]/participants` lists up to 200). Derived text such as a stored AI analysis summary is not rewritten.

## Operational safeguards
- Workspace rate limits (`lib/workspace-rate-limit.ts`, same `rateLimit` interface as the audience limits, which stay per IP and per participant token): `WORKSPACE_LIMITS` per hour for `export` (event CSV), `zip` (event ZIP and the workspace export job), `ai` (analysis starts) and `invitation`. A route calls `workspaceRateLimited(request, auth.workspaceId, action)` after auth, validation and plan checks and returns the result when not null: 429 `{error, retryAfter}` plus a `retry-after` header. A new costly host action adds a key to `WORKSPACE_LIMITS`.
- Global AI cap: `AI_GLOBAL_DAILY_CAP` (default 1000, 0 pauses AI) counts every `ai_calls` row of the UTC day, of all workspaces and deleted events. `assertAiNotPaused(db, now)` (lib/ai/usage.ts) runs first in the analyze route, before plan checks, and answers 503 `{error: "AI is paused for today", reason: "ai_paused"}`; `reserveAiCall` also stops at the cap (`daily_cap`), so a running job cannot pass it. It is separate from `AI_DAILY_CALL_CAP`, which only makes analysis fall back to keywords. Tests pass `now` and `vi.stubEnv`; there is no operator alert yet (US-015).

## Platform operator
- `lib/operator.ts`: `isOperator(user)` is true for a user whose email is in `OPERATOR_EMAILS` (comma list, any case, read per call) AND whose email is verified AND who has no pending password change; nothing in the app grants it. `/ops` (page, `notFound()`) and `/api/ops/*` (`requireOperator`, 404 with the same body as for anyone else) never reveal themselves; the nav link ("Operator") is built in `AppShell` from `isOperator`. A new ops route calls `requireOperator`, never `requireMember`: operators act outside the workspace role model.
- `lib/ops-workspaces.ts` `listOpsWorkspaces(db, {q, page}, now)`: 25 per page, newest first; `plan` is the effective plan (`resolveEntitlements`, override included), `status` the stored subscription status (null = never subscribed; there is no workspace suspension until US-016), seats = active members + unexpired pending invitations, AI calls are attributed through events like `getUsage`. Search is a literal substring of the workspace name or any owner's email.

- Operator actions (`lib/ops-actions.ts`, routes under `/api/ops/workspaces/[id]/`: `suspend`, `reactivate`, `plan-override` PUT/DELETE, `members/[userId]/reset-2fa`; all behind `requireOperator`): a reason (1-300 chars) is required for suspend and override, the override also needs an end date within 366 days and writes the existing `subscriptions.plan_override*` columns (row created for a Free workspace); the 2FA reset removes the account's secret and recovery codes and calls `setSessionsValidAfter` (2FA belongs to the account, so it applies in every workspace). Each success is audited as `operator.<verb>` (`recordOperatorAudit`, actor label `operator:<email>`) into the workspace's own log, and `/ops/activity` (`listOperatorActivity`) lists every `operator.*` row platform-wide; metadata may hold the reason, so write reasons a customer can read. `/ops/workspaces/[id]` is the screen; `/ops` also shows `getOpsAiStatus` (provider, model, today's `ai_calls` vs `AI_GLOBAL_DAILY_CAP`; never a key) and its Test connection button posts to `/api/ai/test`, which lets an operator through without a workspace role.
- Suspension (`workspaces.suspended_at/suspended_reason`, `lib/workspace-suspension.ts`): `requireMember` answers 403 `{reason: "workspace_suspended"}`, `getSessionMember` returns null, host/moderator sockets are refused (and dropped on suspend via `revokeMemberSockets`), and `redirectIfTwoFactorMissing` (now also the suspension check; every workspace page already calls it) sends members to `/account/suspended`. Audience side: every route that reads a participant cookie starts with `eventUnavailableResponse(request, eventId)` (403 `{reason: "event_unavailable"}`, neutral text, no reason), plus `/api/join`, the survey join, the socket participant check and the `/e/[eventId]` and `/survey/[id]` pages (`EventUnavailable`). A new participant-facing route must add that call before it reads the token. Account-level routes that use `getSessionUser` directly stay open (switching workspace, account delete).

- Branding (`workspaces.brand_accent`, `lib/brand-accent.ts`, client-safe): `PATCH /api/workspaces/active/branding {accent}` needs `branding.manage`; setting needs the `branding` entitlement (`assertBranding`, 402 `branding`, Team; `brandingLock` for the UI) and AA contrast, removing (`null`) needs neither. One hex is stored (lowercase `#rrggbb`, check constraint); light uses it as is, dark uses `darkAccent(hex)` (mixed toward white until it passes), because one colour cannot reach 4.5:1 on both the cream and the near-black surfaces. `checkAccentContrast` checks text-on-accent, accent-on-`--bg` and accent-on-`--surface` in both themes and returns `failures` worst first; `contrastFailureMessage` takes a translate function so server and client share the text. `SURFACE_TOKENS`/`INK_CHOICES` mirror globals.css and DESIGN.md (a test compares them). The accent must only be applied to screens while `limits.branding` holds (downgrade lifts it without a write). Logo upload: see docs/branding.md.
- Branding applied (`lib/branding.ts`, `lib/brand-style.ts`, `components/brand-style.tsx`): the join page, `/e/[eventId]`, `/survey/[id]` and `/present/[eventId]` read the accent with `workspaceAccent`/`eventAccent`/`eventAccentByJoinCode`/`interactionAccent` (null without the `branding` entitlement) and render `<BrandStyle accent>` plus `{...brandAttrs(accent)}` (`data-brand`) on their root. `brandCss` re-checks AA and only sets `--accent`, `--accent-ink` and `--focus` under `[data-brand]`, per theme (system preference unless `data-theme`), so every rule that reads the tokens follows and nothing else hardcodes the colour; a failing or malformed stored value renders nothing. A new audience or presenter page must do the same; dashboard pages keep the default accent on purpose. The settings section is `BrandingSettings` on `/dashboard/settings` (`branding.manage`): live preview per theme (painted from `SURFACE_TOKENS`, which now holds `ink` too), a contrast table, Apply and Remove; under `brandingLock` the form becomes a `PlanHint` and only Remove stays.

## Jobs and health
- `lib/jobs.ts`: `runWithRetry(work, {delays?, sleep?, onAttempt?})` tries a job once plus up to 3 retries with backoff (`JOB_RETRY_BACKOFF_MS`, default 1 s, 5 s, 20 s; tests/setup.ts sets zeros) and never throws; `errorClass(error)` gives `Name` or `Name:code` and never the message, which is all that may be stored or logged (`attempts` and `error_class` columns on `note_analyses` and `workspace_exports`). Errors with `retryable: false` (`permanentError`) or code `not_configured`/`event_cap`/`daily_cap` are not retried. `recordJobRun(name, work, db)` writes `job_runs` (last start, finish, status, error class) and rethrows; the two daily sweeps use it (`DAILY_JOBS`: `subscriptions`, `retention`). A new background job uses these two helpers instead of its own try/catch.
- `GET /api/health` (`getHealth`, lib/health.ts): 503 only for an unreachable database or pending migrations; otherwise 200 with `dailyJobs` and `jobRunner` (`exports`, `analysis`: `state` idle/busy/stuck by the job's own timeout, counts, failures in 24 h, last error class). It returns counts, times and classes only, never configuration or content; a test checks that. A new job type with a status table adds a `jobState` call there.

## Sessions and passwords
- Session tokens are `userId.issuedAtMs.expires.sig`; `getUserFromToken` rejects tokens issued before `users.sessions_valid_after`. Changing or resetting a password goes through `setPassword` (lib/auth/password-reset.ts), which sets that column, clears `must_change_password` and must be followed by a fresh `sessionSetCookie` for the current device.
- While `must_change_password` is true, `requireAdmin`/`requireMember` return 403 `{reason: "password_change_required"}`, `getSessionMember` returns null, and server pages redirect to `/account/password`. A route that calls `getSessionUser` directly must call `denyIfPasswordChangeRequired` unless it is `/api/auth/me`, logout or the change-password route.

- 2FA (`lib/auth/two-factor.ts`, `pending-two-factor.ts`, routes under `app/api/auth/2fa/`): a route that signs someone in from a password or a link must check `getTwoFactorStatus(...).enabled` first and hand out a pending token (login) or no cookie (reset) instead of a session. `verifySecondFactor` takes an authenticator or recovery code in one field; a spent recovery code and a disable call end other devices with `setSessionsValidAfter`. Tests stub `TWOFA_ENCRYPTION_KEY` and reset the rate-limit store.
- 2FA screens: `/account/security` (`SecuritySettings`; server page passes `getTwoFactorStatus`, `isTwoFactorConfigured`, `remainingRecoveryCodes`) and the login code step (`TwoFactorStep` in `components/auth-form.tsx`; the pending token lives in component state, never the URL). The QR is drawn in the browser with `qrcode` from the `otpauth://` URI, so the secret goes to no service. Recovery codes exist only in component state after confirm; reloading loses them, and there is no regenerate route yet. In dev `server.ts` lets `.env.local` override shell variables, so `npm run dev` always uses the dev DB; to screenshot against the test DB build with `NEXT_DIST_DIR=.next-shot npx next build` and run `NODE_ENV=production DATABASE_URL=$TEST_DATABASE_URL npx tsx server.ts` (dev `next dev` also rewrote `tsconfig.json`/`next-env.d.ts` and looped on reload: `git checkout` them).

- Workspace 2FA requirement (`workspaces.require_2fa`, `lib/auth/two-factor-policy.ts`): `twoFactorSetupRequired(workspaceId, userId)` is true when the flag is on, the plan still has `enforced2fa` (a downgrade lifts it without clearing the flag) and the member has no confirmed 2FA. `requireMember` answers 403 `{reason: "two_factor_required"}`, `getSessionMember` returns null, host/moderator sockets are refused and server pages call `redirectIfTwoFactorMissing(workspaceId, user.id)` right after the membership is resolved (a new workspace page must add it). Routes that use `getSessionUser` directly (`/api/auth/*` including `2fa/*` and logout, `/api/workspaces/active`) stay open on purpose, so a held member can enrol. `PATCH /api/workspaces/active/security {require2fa}` needs `members.manage`; turning it on also needs `enforced2fa` (402 `enforced_2fa`, `assertCanEnforceTwoFactor`) and `isTwoFactorConfigured()` (503), turning it off needs neither. `listMembers` returns `twoFactor`; the members page shows it and the switch (`twoFactorLock` makes it a `PlanHint`).

- Audit log (`audit_log`, `lib/audit.ts`): append-only; triggers reject UPDATE and DELETE except the delete a workspace cascade makes (the trigger lets a DELETE through only when the row's workspace no longer exists). `recordAudit(db | undefined, {workspaceId|null, actorUserId?, actorLabel, action, targetType?, targetId?, metadata?, ip?})` is the only writer; it takes a pool or a transaction, strips deny-listed keys (password, token, secret, key, text, note; substring, any case, any depth) from metadata, and on failure logs only the action and error code and returns false instead of throwing. `actor_user_id` has no foreign key (a set-null would be an UPDATE and the trigger refuses it); keep who it was in `actorLabel`. Tests truncate with `truncateAll` (TRUNCATE skips row triggers); a driver error from a trigger is on `error.cause` (Drizzle wraps it as "Failed query").

- Audit entries (US-006): routes call `recordAudit(undefined, {...auditContext(request, auth.user), workspaceId, action, targetType, targetId, metadata})` after the action succeeded (never for a refused one). Account-level events (login, password, 2FA) use `recordAuditForUser(request, user, {action, metadata})`, which writes one entry per active workspace of the person; an unknown email on login writes nothing (no workspace, and a null-workspace row could never be deleted). Billing entries (`billing.plan_changed`, `billing.canceled`, actor `billing:<provider>`) are collected inside `applyBillingEvent`'s transaction but written after the commit, because a failed insert would abort the subscription update. Actions are `area.verb` names (`auth.login`, `member.role_changed`, `event.exported`, `ai.analysis_started`...). Never put emails, names of people, request bodies or note text in `metadata`; ids and roles only (event and template names are allowed).

- Audit log page (`/dashboard/audit`, `AuditLog`; `GET /api/audit?action&actor&from&to&page`): needs `audit.view` (owner, admin) and the `auditLog` entitlement (`assertAuditLog`: 402 `audit_log`, tier Team; the page shows `auditLogLock` as a `PlanHint` instead of entries, the nav link shows for every role with `audit.view`). `lib/audit-query.ts` holds `listAuditEntries` (newest first, `AUDIT_PAGE_SIZE` 50, `from` inclusive / `to` exclusive instants, actor is a literal case-insensitive substring of `actor_label`), `listAuditActions` and `parseAuditFilters`. Times render in the browser's zone (`useSyncExternalStore`, "UTC" on the server so hydration agrees) with the UTC value in text and as `title`; the client turns the date inputs into local-day instants. Action names are shown raw (no i18n per action).

- Retention (`lib/retention.ts`): `workspaces.retention_days` (null, 30, 90 or 365; check constraint) and `events.deletion_notice_sent_at`. `PATCH /api/workspaces/active/retention {retentionDays}` (`members.manage`, audited as `workspace.settings_changed`) goes through `setRetentionDays`, which clears every event's notice when the value changes. `runRetention(db, now)` (daily via `startRetentionSweep` in server.ts) emails owners and admins once per event from `ends_at + days - 7` on, and deletes an event (cascade) only when it is past `ends_at + days` AND its notice is at least 7 days old, so an event that was never warned (retention turned on late, job down) is warned first and goes a week later. No reachable recipient or a failed send leaves the notice unset and retries on the next run. The audit entry is `event.retention_deleted` (actor `system`, ids and `retentionDays` only, no name). Mail is sent in `DEFAULT_LOCALE` until events have an audience language (US-019).
- Retention UI: constants and the delete-date rule live in client-safe `lib/retention-schedule.ts` (`deletionDate` = later of `ends_at + days` and notice + 7 days, or today + 7 days when no notice was sent, exactly what `runRetention` emails; `deletionIsNear` = within 7 days; days shown as UTC `YYYY-MM-DD`). `lib/retention.ts` re-exports the constants but imports the database, so client components import the schedule file only. `/dashboard/settings` (`members.manage`, `RetentionSettings`, nav link "Settings") is the home for workspace-level settings; `EventManager` takes `retentionDays` and each event's `deletionNoticeSentAt` for the badge; the event page shows a notice with a primary ZIP download when deletion is near, else a one-line date.

- Workspace export (`workspace_exports`, `lib/workspace-export.ts`; permission `workspace.export`, owner only): `POST /api/workspace/export` queues a row and `scheduleWorkspaceExport` builds the ZIP in the server process after the response (202 `{id}`; 409 `export_running` while one is queued or running, enforced by a partial unique index). The file is kept in the row's `zip` bytea, so it goes with the workspace; `GET /api/workspace/export/[id]` returns the status (never the file) and a `downloadUrl` signed with SESSION_SECRET for 5 minutes, which `/download` checks together with the owner's session. `sweepWorkspaceExports` (hourly, `startWorkspaceExportSweep` in server.ts) nulls files 24 hours after they finished (`expired`, download answers 410); at start `failInterruptedWorkspaceExports` fails rows a dead process left. The ZIP is `events/NN-name/` (`event.json` + `buildEventFiles` CSVs), `templates.json`, `members.csv` (email, role), `plan.json`; a new data table that must be in the export is added in `buildWorkspaceZip`, and `tests/workspace-export.test.ts` scans the output for participant ids and tokens, IPs and password hashes. Audited as `workspace.export_requested` and `workspace.export_downloaded`. There is no screen for it yet.

## Plans
- `lib/plans.ts` is the only place that defines tiers (`PLANS`, `PLAN_PRICES`, `PAST_DUE_GRACE_DAYS`) and the only way to read limits is `getEntitlements(workspaceId)`; never read `subscriptions` directly for a limit. A workspace with no `subscriptions` row is Free, so new workspaces need no row. Month boundaries come from `utcMonthBounds()`.
- Limits: `lib/limits.ts` (`assertTypeAllowed`, `assertCanCreateEvent`, `PlanLimitError`, `planLimitResponse`) and `lib/seats.ts` (`assertSeatAvailable`) throw `PlanLimitError`; routes catch it and return 402 `{error, reason, requiredPlan}`. New limit checks follow that shape. Usage limits live in `lib/limits.ts` too: `assertParticipantSlot` (join route, 403 with the message only, no upgrade hint, under a per-event advisory lock), `assertAiCallsAvailable` (analyze start; the env caps in `lib/ai/usage.ts` still apply) and `assertReportFormat` (export). Tests narrow `PLANS.<tier>` for one case and restore it in `afterEach`; analysis tests and e2e need `setPlan(..., "pro")` / `setPlanFor(email, "pro")` because Free has no AI calls. Tests that need more than Free allows (invites, members, many events) call `setPlan(db, workspaceId, "team")` from `tests/helpers/db.ts`.
- Grace and expiry: `subscriptions.past_due_since` is set by `applyBillingEvent` when status first turns `past_due` (kept while it stays so, cleared by any other status); `resolveEntitlements` gives the paid plan until that date + `PAST_DUE_GRACE_DAYS`, so reads never need the job. `expireSubscriptions` (lib/billing/expire.ts, run daily from server.ts) only writes `plan: free` back and returns the workspaces it changed; it is the hook for work that must happen once when access ends. Pass `now` to `applyBillingEvent`, `expireSubscriptions` and `getEntitlements` in tests instead of faking timers.
- Locked hints: a gated control stays visible as `<PlanHint lock={{requiredPlan}}>` (components/plan-hint.tsx, a link to `/dashboard/plan` that names the tier). Server pages build the locks from `getEntitlements(...).limits` with `lockedTypes`, `lockedFormats`, `aiLock`, `seatLock` (lib/plan-hints.ts) and pass them down; client components never import `lib/plans` values. Usage numbers for the plan page come from `getUsage` (lib/usage.ts).

- Downgrades never delete: `lib/over-limit.ts` decides read-only content from the current entitlements (nothing stored): an interaction whose type the plan lacks, and events created this UTC month past `eventsPerMonth` (oldest kept). Start, PATCH, duplicate, create-in-event and reorder call `assertNotOverLimit`, which throws `PlanLimitError("over_limit")` answered 403 (not 402) with `requiredPlan`. Close, pause, delete, results and CSV stay open. Pages pass `itemLocks`/`eventLock`/`lock` down.
- Seats after a plan change: `reconcileSeats(workspaceId)` (lib/seats.ts) suspends the newest active members beyond the seats (`memberships.suspended_reason = 'seat_limit'`, never the last active owner) and reactivates only those, oldest first, while seats plus pending invitations allow. It runs after a billing webhook, the daily sweep, member removal/suspension, invitation revoke and on the members page/list. A manual status change clears the reason, so manual suspensions are never lifted by the plan.

## Billing
- `lib/billing/`: `BillingProvider` (createCheckout, createPortalSession, cancelSubscription, parseWebhook), selected by `getBillingProvider()` from `BILLING_PROVIDER` (unset = mock outside production, none in production → routes answer 503). A paid-to-paid change on a live non-mock subscription goes to the portal (`changeVia`), never a second checkout. Navigation away uses `goTo` (lib/go-to.ts) so tests can mock it.
