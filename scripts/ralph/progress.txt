- Files: lib/auth/pending-two-factor.ts, lib/auth/two-factor.ts (`verifySecondFactor`, `disableTwoFactor`), lib/auth/password-reset.ts (`setSessionsValidAfter`), app/api/auth/login + reset routes, app/api/auth/2fa/*, lib/i18n en/id, tests/two-factor-routes.test.ts.
- **Learnings for future iterations:**
  - The pending token is `2fa-pending.<userId>.<expires>.<sig>` (5 min, signed with SESSION_SECRET); the prefix is signed, so it never parses as a session token. A bad token, an expired one and a wrong code all return the same 401 `api.twoFactorInvalid`; a wrong password on login stays the usual `api.loginInvalid`.
  - A recovery code at login and a successful disable call `setSessionsValidAfter` (other devices drop) and then issue a fresh cookie; enabling 2FA touches no session. An authenticator code at login leaves other sessions alone.
  - `POST /api/auth/reset` withholds the cookie when the user has 2FA (`{ok, loginRequired: true}`), so an emailed link cannot replace the second factor. The reset form still pushes to /dashboard, which redirects to login; US-003 may want to route it to /login directly. Invitation accept only signs in brand-new accounts, which have no 2FA.
  - A user with 2FA on while `TWOFA_ENCRYPTION_KEY` is missing gets 503 at login rather than a password-only session.
  - Attempt budget stays one key per user (`2fa:<userId>`), shared by confirm, verify and disable; verify also has a per-IP limit (30 per 15 min). The enrolment confirm uses one attempt, so route tests count that when probing the limit.
  - tests/totp `totp(secret, timeMs)` needs the time argument; route tests wrap it as `totp(secret)`.
